# PI11 end to end: chat fishing (`!fish`) on the lane's own stack

This check runs chat fishing against the real realm. Two SIMULATED chatters are present in a SIMULATED live stream.
A `!fish` from one of them puts a float at the pier in her window's light colour, and the fish is kept with `via`
`chat`. The public pier feed, the Almanac and Postgres all show it. The run also checks the rate limits, a deleted
`!fish`, a timeout, and that ordinary chat is not claimed. The run plays Herald over HTTP with the realm's real
Herald secret. Real Twitch is never touched.

## Run it

```bash
work/lanes/pier/e2e/run-chat.sh
```

`PIER_E2E_SKIP_BUILD=1` reuses the realm build and the web build in `/tmp/chatdom-pier-e2e-web`
(`PIER_E2E_WEB_DIST`); without it both are built first. The web build gets no database variable.

`run-chat.sh` loads `DATABASE_URL` from `/srv/chatdom/chatdomgg/.env` without echoing it. To use another
file, set `PIER_E2E_ENV_FILE`. It pins `REALM_DATABASE_SCHEMA=pier` and runs at `nice -n 10`. It writes:

- `work/evidence/pier/pi11-chat-run.json`, which records:
  - every step with its start and duration
  - every request the mock Herald sent, with the realm's answer
  - every pier feed event with its time
  - the presence frames for the chatters' windows
  - the speech cues seen on the kingdom watch
  - the Almanac before and after
  - the Postgres rows checked
- `work/evidence/pier/pi11-chat-run.log`, the console log. Connection strings and the Herald secret are scrubbed from
  it. `*.log` is ignored by git, so add it with `git add -f`.
- A failed run writes `pi11-chat-run-failed.json` and `.log` instead, so it never replaces the last passing evidence.

You can change these settings:

| Setting | Default | What it does |
|---|---|---|
| `PI11_FIRST_CHATTER`, `PI11_SECOND_CHATTER` | `990200001` (saoirse_k), `990200002` (quiet_one) | The simulated Twitch ids |
| `PI11_MAX_CASTS` | 4 | How many casts saoirse_k gets to land a fish (escaped, snapped, missed or broken lines are cast again after the rest) |
| `PI11_QUIET_CASTS` | 3 | How many casts quiet_one gets after her timeout to land a fish that shows no name |
| `PIER_E2E_SKIP_BUILD=1` | off | Reuses `apps/realm/dist` |
| `PIER_E2E_STACK`, `PIER_FOUNDED_SCENE`, `PIER_FOUNDED_MANIFEST` | as in the PI10 run | The founded directory and the hash-checked copy of tobi4s_'s founded scene |

**Ports.** The run uses one free port in 5170–5186 for the realm. It checks the port with a bind test right before
use. It never uses 5187 or 5190–5199. The realm binds 127.0.0.1 only and is stopped at the end, whether the run
passes or fails. No API process is needed: nobody walks.

## What it runs

1. **The PI10 setup.** The run verifies the copied scene against its live receipt and builds the realm. It migrates
   schema `pier` and adopts the copied plan for kingdom 129634568 as a simulated-origin layout. The adoption is
   idempotent and answers `unchanged` after the first run.
2. **The realm** (`apps/realm/dist/realm.mjs`). It runs with these settings:
   - `REALM_SIMULATED=1`, `REALM_STORAGE=postgres` and `REALM_PIER_FISHING=1`
   - a fresh random `REALM_INGRESS_HERALD_SECRET` for each run, which is never printed
   - `REALM_ENTRY_KINGDOM_ID=129634568` and `REALM_ENTRY_KINGDOM_NAME=Willowmere`

   A chatter's home is furnished only under an approved kingdom name (`evening/citizens.ts` `furnish`). The child
   process gets only `PATH`, `HOME`, `DATABASE_URL`, the schema and its own settings.
3. **Holding the kingdom open.** The run opens the public kingdom watch (`GET /api/realm/watch/129634568`). The watch
   retains the kingdom for as long as it is open, and its frames show whose windows are lit and which speech bubbles
   appear. Ingress also holds a kingdom for 180 s after each observation. The mock Herald beats every 30 s: it reports
   the stream live and sends an anonymous partial Chatters sweep of both chatters. This keeps the presence frame
   fresh (a frame older than 90 s lights no window for speech) and keeps both leases alive. No walker is needed.
4. **The mock Herald.** Each request is first validated against the realm's own schemas (`PresenceInputSchema` and
   `RealmHeraldEnvelopeSchema`), so any refusal comes from the realm. It sends the same messages as
   `apps/herald/src/source/observations.ts` and `realm-delivery/delivery.ts`:
   - The stream: `{kind: 'stream', live: true, sessionId}` on `POST /internal/realm/ingress`.
   - A chat message: a `chat` presence observation (`id chat:<messageId>`, named), then
     `{chat: {id: messageId, personId, asOf, expiresAt: asOf + 10 s, parts}}` on `POST /internal/realm/herald`.
   - A deleted message: `chatCleanup` `remove` plus a Forge `cancel`.
   - A timeout: `chatCleanup` `clear` for the person plus a Forge `clear`.

   Times are stamped on the database clock, sampled at the start and set 250 ms early, so they are never in the
   realm's future. A cold open can still answer 503, and the same idempotent observation is then sent again.
5. **The steps:**
   1. Both chatters are observed in chat. `citizens.observe` settles each one into a home, and the run waits for a
      presence frame where both windows are lit under their names. Their deeds' slots must be those windows.
   2. The run opens the pier feed (`GET /api/realm/pier/watch/129634568`) and records every event. It reads the
      Almanac.
   3. saoirse_k sends `!fish`. The run expects these events:
      - a `line` `float` with her name, her window slot, `pierLightColour(slot)` and `via` `chat`
      - then `bite`, `fight` and `caught`
      - if the line ends `gone` or `broken` instead, she casts again after the 45 s rest, up to `PI11_MAX_CASTS` times
   4. Rate limits. A second `!fish` while her line is out is answered `relayed` (claimed), and for 4 s it makes no
      other line, no `full` event and no speech bubble. A `!fish` straight after the line ends is also claimed, and for
      4 s it makes no line.
   5. The catch. These must hold:
      - The `realm_fishing_catches` row exists with `record->>'via' = 'chat'`, her owner id and the same fish.
      - The fish item exists in `realm_items`.
      - On a kingdom first, the `keepsake:mount.*` item exists.
      - The Almanac page is `caught` and counts the catch.
      - On a kingdom first, `first` is `{name: 'saoirse_k', via: 'chat'}` and `mounts` equals the kingdom's mount
        number (at least 1).
      - When the species was already caught, the earlier first stays the first, and her fish is the biggest if it
        weighs more.
   6. Deletion. quiet_one sends `!fish` (message X), then a `remove` for X arrives. The run expects `gone` with
      reason `pulled`.
   7. Timeout. quiet_one sends `!fish`, then a `clear` for her person id arrives. The run expects:
      - `gone` with reason `cleared`
      - a row in `realm_pier_hidden_names`
      - her name nowhere in the Almanac
   8. After the rest, quiet_one fishes again. Her floats carry `name: null`. If she lands a fish, the `caught` event
      has `name: null`, and the Almanac reads `null` wherever her catch is the first or the biggest.
   9. saoirse_k says "hello". It is relayed as speech: a chat cue at her slot appears on the kingdom watch, and the
      pier feed stays silent for 4 s.
   10. Neither the pier feed nor the Almanac ever contains a person id.

## What it does not prove

- **Herald is simulated.** This run proves the realm side of the private Herald route. Herald's own Twitch ingest
  (EventSub to these messages) is covered by Herald's tests.
- **Some state lasts between runs.** Schema `pier` keeps deeds, catches and hidden names from earlier runs. On a
  rerun, quiet_one's name is already hidden from the start (`before.hidden` in the JSON), so her first floats also
  carry `name: null`. saoirse_k's catch is a kingdom first only if nobody has caught that species here before.
- **Chat lines live in memory.** A realm restart loses the floats in the water by design. The kept fish is durable,
  and the PI10 run proves that.
- **The stream view is the chat presenter, not the whole stream page.** The run draws the realm's real public feed
  in the lane's build (`/-/pier?view=chat&feed=live&kingdom=129634568`, `vite preview` of `/tmp/chatdom-pier-e2e-web`
  proxied to this run's realm) at 1920x1080 on SwiftShader. It saves `pi11-chat-run-float@1920x1080.png` (her float
  and name in the water) and `pi11-chat-run-stream@1920x1080.png` (her catch's card and leaping fish). The page is
  armed with `holdOn('line' | 'caught', seconds)` to stop its own clock when that beat arrives: software frames on a
  busy host can outlast a card. The grand stream page (`/stream`) mounts the same presenter through the pier
  kingdom layer once grand-world's kingdom-layer seam lands (SEAMS 3a); its look on a real GPU is in the
  `pi11-chat-stream-*` stills and clip.

## Files

- `run-chat.sh` loads the environment and runs the check.
- `pi11-chat.mjs` is the orchestrator. It handles the port, the build, migration, adoption, the realm, the mock Herald,
  both feeds, the steps and the evidence.
- `pi11-support.ts` holds the shared contracts the mock Herald validates against, the plan adoption, and the read-only
  database checks. Its pool sets `default_transaction_read_only=on` with `search_path=pier`.
