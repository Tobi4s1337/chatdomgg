# Chatdom voxel content

The source format is `VoxelBlueprint` from `@chatdom/shared`. Blueprints are pure deterministic TypeScript:
version 1, build lattice (0.125 m), half-open integer XYZ boxes, a registered `styleId`, and explicit window
anchors. Box order matters: material zero carves earlier solids. Do not add fields to the strict schema.
`src/materials.ts` owns all material IDs and the Hearth, Tide and Grove kits. No authored color literals,
registry mutations, baked emissive windows, clock, network or global randomness belong in asset factories.

## Collection entry points

The main-owned `src/catalogue.ts` discovers these modules with Vite's module glob. Each lane exports a nonempty
`BLUEPRINTS: readonly VoxelBlueprint[]`; a missing collection is an error, never a fallback to core.

| Command collection | Entry module | Required order/count |
|---|---|---|
| `core` | `src/core/index.ts`, generated by catalogue | 45 homes, three castles, three trees |
| `homes-hearth` | `src/homes/hearth/index.ts` | emberfold, bramblecross, heatherstead × hut, cottage, house, manor, hall; 15 |
| `homes-tide` | `src/homes/tide/index.ts` | gullstep, saltbend, keelcroft × same tier order; 15 |
| `street-props` | `src/props/street/index.ts` | Hearth then Tide, ten forms each; 20 |

Home IDs are `home-<style>-<family>-<tier>`. Street IDs are `street-<style>-<form>`, where forms, in order, are
fence-straight, fence-corner, fence-end, wall-straight, wall-corner, wall-end, flower-pot, flower-trough,
rock-cluster and leafy-shrub. Lane modules also export their factories as specified in specs 04–06.

## Palette and budgets

Lane homes use their kit's wall, roof, trim and stone plus air/glass and restrained earth, bark, leaf, moss,
petal or blueFlower accents. Street props use kit trim/stone plus those natural accents; no wall, roof or glass.
All materials are existing registered keys, not palette offsets. Core assets include registered civic accents
and remain baseline fixtures rather than substitutes for the authored lane families.

| Budget | Lane home | Street prop |
|---|---:|---:|
| Source boxes | 2,000 | 512 |
| Occupied cells | 1,000,000 | 20,000 |
| Actual meshed triangles | 250,000 | 40,000 |
| Draws per independently rendered model | 1 | 1 |

Shared limits also apply: 20,000 source boxes, 64 windows, dimensions 1–256 cells and at most 16,777,216 padded
cells. Lane homes reserve exactly `[64,160,128]`; tier active depth grows backward from +Z in 8/10/12/14/16 m
steps. Locked rear land contains no occupied geometry. Props use the row-specific dimensions in spec 06.
Every connected occupied component must have a structural path through face neighbors to y=0.

Each visible home window has a unique stable ID and a whole in-bounds rectangle. Its center lies on the outward
glass plane: south/east sample glass immediately before the plane, north/west immediately after it. The validator
requires glass somewhere within the rectangle (mullions may cross it), and the first two outward cells across
the whole rectangle must be air. This checks the facade opening without treating another building across a
courtyard as an obstruction. Lane tests additionally prove that roof overhangs, shutters and plants cannot block
the outward facade and that window IDs/entrances persist through growth.

## Validate and render

```sh
pnpm content:validate --collection core
pnpm build
pnpm content:render --collection core
pnpm content:validate --collection homes-hearth
pnpm content:render --collection homes-hearth
```

Validation executes the actual ordered boxes, checks the strict schema, registry, style palette, IDs/counts,
determinism, dimensions, active reserve, ground connectivity, window glass/exterior clearance and lane home
entrance volume, then runs the production skylight solver and greedy mesher. Output reports occupied bounds,
cells, boxes, windows, mesh chunks, vertices, triangles and the one-model draw budget. A home entrance check finds a
supported 10×20-cell passage through the front eighteen depth cells; lane tests must additionally prove the
interior route, threshold heights, supported roof/porch construction and stable family anchors. The generic
validator is not a replacement for those authored geometry tests or visual review.

Rendering uses the built web app, Chrome/SwiftShader, the production `VoxelWorkerPool`, `geometryFromChunks`,
voxel shader and authored dusk environment. It never rasterizes an occupancy plot in place of the material.
The dedicated bench route is `/-/content?collection=core&asset=home-hut-hearth-0&angle=front&hour=19`.
Angles are front/side/back; hour may be changed to 12 or 0 for noon/night review. Models are unoccupied: no fake
presence or people. The readiness flag is set after worker completion, shader compilation and GPU frame completion.
Browser exceptions and console errors fail capture.

Every lane asset gets three 480×480 views under `shots/content/<collection>/`, an embedded SVG contact sheet,
PNG contact sheets captured at 1440×900 and 390×844 viewports, and `render-stats.json`. Contact sheets capture
their complete scrolling height. Core defaults to five representative assets (one home per kit, castle, tree);
use `--all` to render all 51. `--asset <exact-id>` captures one model, `--hour 12` changes light, and
`--base-url http://127.0.0.1:5190` reuses a preview. Otherwise the script owns a temporary preview on an OS-assigned free port
and closes it. Set `CHATDOM_CONTENT_PORT` to pin a port explicitly; parallel lanes should leave it unset. Build again after adding a collection. Open sheets with `view_image`; inspect full-size angles
for roof joins, exposed window planes, thresholds and ground contact. SwiftShader timings are not GPU evidence.

Individual collection captures demonstrate unoccupied models. Additional review modes below capture mixed
streets, prop assemblies, entrance details and labelled simulated windows. Owned lane tests establish exact
joins, route connectivity and structural support; those are not implied by a successful individual render.
No generated painting, placement authority or door behavior is added by this tooling.

## Review scene exports and staged work

`content:validate --collection <lane> --partial` validates a nonempty ordered subset during intermediate lane
tasks, with the same per-model budgets and geometry rules. It does not certify a complete collection. Final
acceptance omits `--partial`. Only finished models belong in `BLUEPRINTS`; unfinished factory inputs may throw.
The validator reports `modelDrawBudget: 1`; actual measured draws come from browser `render-stats.json`.
The front-passage heuristic does not prove threshold/interior connectivity or safe step heights.

The existing capture modes use the same production worker, geometry/material and readiness path:

```sh
pnpm content:render --collection core --scene mixed
pnpm content:render --collection core --scene castle
pnpm content:render --collection core --scene threshold --asset home-hut-hearth-0
pnpm content:render --collection core --scene windows --asset home-hut-hearth-0 --presence off
pnpm content:render --collection core --scene windows --asset home-hut-hearth-0 --presence on
pnpm content:render --collection street-props --style hearth
pnpm content:render --collection street-props --scene joins-hearth
```

`castle` uses the actual twelve-module compound from the world plan, through the same placement factory
the kingdom consumes. It captures front/side/back at 1440×900 and 390×844. These are unoccupied model views;
they do not certify its terrain approach, presence lighting or kingdom camera composition.

`mixed` uses the first family's hut, second family's house and third family's hall (or named core representatives)
with their south facades aligned. Missing required models fail explicitly. It captures 1440×900, 390×844 and
1920×1080. `threshold` captures doorway focus at 480×480. Home lanes export `HOME_REVIEW`, mapping each asset
ID to `{ entrance: [x,y,z] }` in integer build cells. This point sits halfway up the real open doorway; it is
camera data rather than navigation authority, and owned geometry tests establish the route behind it.
`windows` focuses the first authored window and captures 480×480 through the production window-light layer.
`--presence on|off` is required and visibly labelled SIMULATED. No real presence, owner name or surrounding
light transport is claimed by this isolated-pane check.

Street lanes export `JOIN_FIXTURES`, exactly `joins-hearth` and `joins-tide`, each with `instances` containing
`{ assetId, position: [x,y,z], quarterTurns: 0|1|2|3 }`. Positions use integer build cells, with positive Y rotation
around local origin before translation. Include all ten kit forms and the two structural assembly examples
from spec 06, at y=0 and z≥0. The bench adds a matching main-owned core house behind the props as context.
Assembly captures use the same three standard sizes as `mixed`. Tests must verify contacts and overlaps;
a picture does not establish exact join geometry. These exports stay outside strict `VoxelBlueprint` objects
and introduce no placement or socket protocol.

`--style hearth|tide|grove` filters individual assets into `style-<kit>/` output subfolders. Non-default hours
use `hour-<hour>/`; scene modes use `<scene>/`, with `windows-on/` or `windows-off/`, preventing dusk/on/off
captures from overwriting each other. `--asset` adds an `asset-<id>/` directory, preserving complete collection sheets during detail experiments. `render-stats.json`
records scene, presence, models, measured calls and screenshot sizes. All SVG/PNG sheets contain the actual
captured pixels. A missing scene, collection, fixture, browser error or stale scene build is a hard failure.
`pnpm verify` currently captures the standard app surfaces; explicit collection/scene commands are separate.
