# Dock bridge

`handleDock` uses the realm sign-in cookie and server-side session lookup, and requires same-origin plus the session CSRF token for POST. The dock status and action schemas are in `contracts.ts`. Mods can read when the bridge verifies their role; every current dock action is reserved to the broadcaster. No bridge means unavailable.

Set `DOCK_REALM_URL` to the realm service's HTTPS origin (plain HTTP only on loopback) and `REALM_INTERNAL_SECRET` to the shared service credential. The API sends bearer-authenticated JSON to `/internal/dock/status` with `{version:1, origin:'live'|'simulated', principal:{personId,sessionId}, kingdomId}`. The bridge replies with a `DockState` or `null` when access is forbidden. `/internal/dock/action` receives `{version:1, origin, principal, action}` and replies with a `DockOutcome`. The realm must independently check the session is current in that origin, verify broadcaster or moderator status against the kingdom, and atomically recheck the action's role, expected revision, capability, target and eligibility. It must durably deduplicate by kingdom and action ID, rejecting conflicting reuse. An `accepted` response must have a `receipt` and `witness:{actionId,kingdomId,origin,streamEventId}` bound to the request and mean the moment was witnessed by the stream; a committed realm event alone is not a presentation witness. This is an assertion from the trusted bridge, not independent proof; the realm must obtain a real stream presentation acknowledgment before returning it. A mismatched or missing witness is unknown; an uncertain delivery is `unknown`. Neither API nor UI may automatically retry an unknown outcome. The bridge is not currently implemented in the realm; the adapter does not invent observations or stream success.

A bridge may provide `undoable: [{id, kind, label}]` in status (at most 20 entries). `id` is the accepted **receipt ID**, `kind` is the original action kind excluding `undo`, and `label` is an approved public label. When present, only listed receipts may be sent as an undo target; an empty list denies every undo. When absent, the API allows a syntactically valid receipt target through to the realm for its atomic authorization. This optional field does not replace the realm's check.
